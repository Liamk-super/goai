# Human Report Presentation Layer V0.1

## 目标

`user-validation-designer` 保留完整的机器可读研究、证据、评分、复验与 Agent 交接结构，但普通学生产品开发者默认只阅读 `structured_output.human_report`。展示层的任务不是再次分析，而是把已经通过程序校验的结果压缩成可以直接指导下一版开发的短报告。

## 双层输出

### Internal Machine Output

用于 AgentTeams、证据校准、Benchmark、Trace、复验和管理员展开查看。继续保留 Persona、假设、验证计划、Evidence Card、评分、冲突、handoff、执行日志和完整性诊断等结构。

### Human Report

由 `src/presentation.mjs` 确定性渲染，不额外调用模型，也不能新增事实。默认最多六个板块：

1. 谁最需要这个产品；
2. 用户实际表现；
3. 当前最关键的 3 个用户问题；
4. 最多 3 项开发优先级；
5. 最多 2 个下一步验证动作；
6. 最多 3 条仍缺信息。

报告长度上限 1500 个字符，目标阅读时间 1–2 分钟。

## 前台隐藏项

普通报告不得直接暴露内部任务/证据/Persona/假设/计划 ID、状态机步骤、证据等级代码、评分计算、Agent handoff、执行日志、完整性诊断或知识库规则编号。需要审计时仍可从内部结构展开查看。

## 证据边界

- 真实使用/访谈优先于模拟；没有真实材料时必须显式写“AI 模拟推演，仅供参考”。
- “30 天内再次使用”默认称为“30 天内复用”，只有源数据明确按标准 D30 cohort 计算时才可写 D30。
- 尚未正式开放收费时，0 付费只能说明真实付费尚未验证，不能自动写成付费失败。
- 少量访谈只能支持“事件驱动/季节性迹象”，不能写成已证实的季节性结论。
- S4 首体验/任务测试未执行时，不允许由模型凭空产生浏览器、弱网、上传、麦克风等具体体验事实；只有调用方真实用户证据或可信上游产品证据明确支持的体验问题可以保留。

## 开发建议格式

每个进入前台的产品问题都应形成：

`用户表现 → 为什么重要 → 产品怎么改 → 改完看什么`

建议必须落到可开发或可验证动作，避免“提升体验”“增强价值”“优化留存”等空话。

## Golden Case

`examples/offerpilot-human-report.example.md` 是 OfferPilot 真实案例的展示层 Golden Case。它只使用已提供的后台漏斗与访谈信息，不声称执行过缺失的浏览器/任务测试，也不包含 Safari、弱网、上传失败等无来源体验事实。
